# Pixie provenance

Feature `398b1fcc-55b0-4755-8ef8-502aa628c264`. Generated by Pixie's agent chain — this file records *why* the accompanying code changed.

## Outcome

A changelog entry can be marked as breaking, and that marking travels consistently to the changelog page (a pill next to the title, announced to screen readers as `Breaking change:` before the title), the RSS feed (a `[Breaking] ` title prefix and a `<category>breaking</category>` element), and the changelog API (a `breaking` boolean on every entry, filterable with `?breaking=true`).

## What was asked for

A `breaking` boolean flag is added to the shared changelog entry shape used by both `pixie-sandbox/pixie-sandbox-site` and `pixie-sandbox/sandbox-changelog-api`, meaning the same thing in each repository. In the data files the field is optional and omitted when false, so the four existing entries in each repository need no change and continue to render as non-breaking. On the site, a marked entry renders a small `Breaking` pill next to its title on the changelog page, styled in an amber warning colour that stands out from the muted date and reading-time styling, and carrying the accessible text `Breaking change:` in DOM order before the entry heading so a screen reader announces it before the title. In the RSS feed at `/changelog.xml`, each marked entry's `<title>` is prefixed with `[Breaking] ` and its `<item>` gains a `<category>breaking</category>` element; non-breaking entries are unchanged. The changelog API returns `breaking: boolean` on every entry (defaulted to `false` where the source omits the field, so consumers see a consistent shape), accepts `?breaking=true` to return only breaking entries, and responds `400 Bad Request` if the `breaking` query parameter is present with any other value.

## Acceptance criteria

- **AC1** — given a changelog entry with `breaking: true` in `data/changelog.json`, when the /changelog page is rendered, then a visible `Breaking` pill appears next to that entry's title, styled in the amber warning colour and distinct from the muted date and reading-time text
- **AC2** — given a changelog entry with `breaking: true`, when a screen reader reaches that entry on the /changelog page, then it announces the text `Breaking change:` before it announces the entry title text
- **AC3** — given a changelog entry where `breaking` is absent or `false`, when the /changelog page is rendered, then no `Breaking` pill and no `Breaking change:` text appears on that entry
- **AC4** — given a changelog entry with `breaking: true`, when a client requests `/changelog.xml`, then the corresponding `<item>` contains a `<title>` whose text starts with the literal `[Breaking] ` (open bracket, `Breaking`, close bracket, single space) followed by the entry title
- **AC5** — given a changelog entry with `breaking: true`, when a client requests `/changelog.xml`, then the corresponding `<item>` contains a `<category>breaking</category>` element
- **AC6** — given a changelog entry where `breaking` is absent or `false`, when a client requests `/changelog.xml`, then the corresponding `<item>` `<title>` has no `[Breaking] ` prefix and the `<item>` contains no `<category>breaking</category>` element
- **AC7** — given the changelog API is serving from its `data/changelog.json`, when a client requests the changelog list with no query parameters, then every entry in the response body has a `breaking` field of type boolean, with `false` for entries whose source data omits the field and `true` for entries whose source has `"breaking": true`
- **AC8** — given the changelog API is serving a data file containing both breaking and non-breaking entries, when a client requests the changelog list with `?breaking=true`, then the response contains only entries whose `breaking` is `true`, every returned entry has `breaking: true`, and the count matches the number of breaking entries in the source data
- **AC9** — given the changelog API is running, when a client requests the changelog list with the query parameter `breaking` set to any value other than the exact string `true` (for example `false`, `1`, `yes`, an empty string, or a repeated occurrence), then the system responds `400 Bad Request`
- **AC10** — given the four existing entries in `pixie-sandbox-site/data/changelog.json` and the entries in `sandbox-changelog-api/data/changelog.json` at the start of this work, when the change is merged, then none of those existing entries have been modified — their `title`, `description`, and `date` fields are byte-identical and no `breaking` field has been added to them
- **AC11** — given the changelog API is serving a data file where no entry has `breaking: true`, when a client requests the changelog list with `?breaking=true`, then the system responds `200 OK` with an empty list, not `404`
- **AC12** — given two or more changelog entries with `breaking: true` present on the /changelog page, when the page is rendered, then each such entry has its own Breaking pill with its own `Breaking change:` accessible text; a single shared marker at the top of the page does not satisfy this

## Where this was expected to land

- `pixie-sandbox-site/components/changelog/ChangelogEntry.tsx` — Adds `breaking?: boolean` to the exported `ChangelogEntryData` type and renders the Breaking pill (with `Breaking change:` accessible text in DOM order before the title) when the flag is true.
- `pixie-sandbox-site/app/changelog.xml/route.ts` — Local `ChangelogEntry` type here duplicates `ChangelogEntryData` and does not import from the component. Adds `breaking?: boolean` to the local type and emits the `[Breaking] ` title prefix and `<category>breaking</category>` element inside each item whose entry is marked breaking.
- `pixie-sandbox-site/data/changelog.json` — Data source. Existing entries are not modified. Future entries may add `"breaking": true`; absence means false.
- `pixie-sandbox-site/__tests__/changelog/ChangelogEntry.test.tsx` — Existing test file for the component. Gains the acceptance-test cases covering AC1, AC2, AC3, AC12 (added as a new describe block or a new test file alongside — engineer's call on layout).
- `pixie-sandbox-site/__tests__/changelog-xml-route.test.ts` — Existing test file for the RSS route. Gains the acceptance-test cases covering AC4, AC5, AC6.
- `pixie-sandbox-site/__tests__/changelog-data.test.ts` — Existing data-shape test. Does not currently reject unknown fields, so today it would not fail on a `breaking` addition. The engineer extends it to accept `breaking?: boolean` and reject non-boolean values where present.
- `sandbox-changelog-api/src/server.ts` — The API entry point per the repo's `package.json` (`node src/server.ts`). Adds `breaking` normalisation on every response entry (`false` when source omits it), adds `?breaking=true` filter, and 400s on any other value of the `breaking` query parameter. The exact file among `src/`'s three files that hosts `handle()` and its query parsing may be `server.ts` or a sibling — engineer picks (see deferred_decisions).
- `sandbox-changelog-api/data/changelog.json` — The API's own copy of the shared data file. Existing entries are not modified; the shape gains an optional `breaking?: boolean` going forward.
